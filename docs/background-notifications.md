# Android 后台通知方案（待实施）

## 当前状态

应用目前没有后台推送实现。Supabase Realtime WebSocket 只用于应用活跃且连接存续时同步；Android 将应用挂起或清理进程后不保证连接，因此不能把 Realtime、心跳或定时补拉描述为离线通知。本文是实施建议，不表示服务已开通、代码已接入或真机已验收。

## 建议架构

国内 Android 优先评估 DCloud uni-push 与可用的厂商离线推送通道，不默认依赖 Google 服务或 FCM。建议事件路径：

`Supabase Database Webhook -> 受信任服务端或 Edge Function -> uni-push 服务端接口 -> Android 客户端`

Supabase 可继续承担 Auth、数据库、Storage 和 Realtime，不必强制迁移到 uniCloud。Webhook 接收端应验证来源并只接受允许的事件；中间服务根据业务规则决定是否发送和发给哪个设备，不应让客户端直接持有推送服务端凭据。

## 接入前置条件

- 开通并配置 DCloud 推送服务。
- 固定 Android 应用包名和签名，并在 DCloud 与目标厂商控制台配置一致。
- 按所选厂商和设备覆盖范围完成离线通道、应用资质及控制台要求；部分设备或系统策略下仍可能无法及时送达。
- 客户端完成推送初始化、权限/通知渠道处理，并在登录后将当前账号对应的 CID 安全绑定到服务端。
- 所有 uni-push 服务端密钥、Webhook secret 和厂商凭据仅存于受信任服务端的密钥管理配置，不进入 App、客户端配置或版本库。

目前没有相应凭据与配置，因此这里不提供伪造的发送实现或声称通知已可用。

## 身份、可靠性与隐私

- 设备绑定和解绑必须由已认证用户发起，并在服务端校验该用户对设备记录的所有权。CID 应与账号及应用/环境范围关联；切换账号时先解绑旧账号关系，再绑定新账号。
- 退出登录时解绑当前设备与账号的关系；服务端还应处理失效 CID，避免旧设备继续收到账号通知。
- Webhook 与推送发送需设计有限重试和退避；以事件 ID/业务记录 ID 做幂等去重，防止重试造成重复通知。记录投递结果但避免记录敏感正文或凭据。
- 通知默认不放聊天正文、私密笔记内容、邮箱等敏感信息。建议使用中性提示，点击通知后由用户完成必要的登录/解锁，再通过受 RLS 保护的接口恢复并加载聊天。
- 点击通知应使用稳定的路由/业务标识打开应用并恢复到聊天上下文；不要把访问令牌或敏感内容放入推送 payload。
- 推送仅作提醒，不是消息数据源或送达保证。应用恢复前台后仍应通过 Supabase 查询补齐消息，并按消息 ID 去重。

## 验收边界

部署后需在真实 Android 设备及目标厂商系统上分别验证前台、后台、进程被清理、锁屏、通知权限关闭、账号切换、退出解绑、无效 CID、重试去重及通知点击恢复聊天。不同厂商、省电策略和系统版本会影响离线送达，不能仅凭服务端返回成功宣称用户已收到。当前没有真机推送验收。
